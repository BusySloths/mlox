model failure, live.

A real model on a real Kubernetes cluster starts giving wrong answers without throwing a single error. MLOX notices, points to the broken step, and an AI assistant explains the cause and proposes a fix. A person decides.

The demo in four acts

From normal traffic to a diagnosed incident and back.

Everything you see runs on our own servers: a model served from Kubernetes, telemetry flowing into a time-series database, and the MLOX terminal UI watching it all.

ACT 1 · SET UP

Users and operator

A traffic simulator plays the users. The MLOX TUI plays the operator's control room.

ACT 2 · OBSERVE

Learn what is normal

MLOX discovers the pipeline from its telemetry and calibrates a baseline from the first runs.

ACT 3 · BREAK

Inject a hidden fault

One step inside the model goes wrong. Requests still succeed, but predictions drift.

ACT 4 · RECOVER

Explain, fix, learn

MLOX flags the step, the assistant tells the story, and the pipeline recovers once the fault is gone.

4How MLOX sees a pipeline

Pipelines are discovered, not drawn by hand.

The model reports each step it runs as a span in one trace. MLOX assembles those traces into a pipeline and keeps, for every step, how long it took and what its output looked like. Nobody configures the structure.

input.normalizescales the raw features
pca.transformcompresses them to principal components
regression.predictturns components into a prediction
quality.evaluatecompares predictions with labels (RMSE)
Step 1 · seconds

Early-detection anomaly models

  • Fast statistical and ML detectors watch every step and signal.
  • One-class models learn normal from historical runs, no labels needed.
  • Short and long windows catch both sudden and creeping change.
  • Deviations are traced through the pipeline graph to their origin.
Step 2 · automatic or on demand

Reasoning: investigation and mitigation

  • Starts as soon as step 1 raises an incident, or when an operator asks.
  • Reasons over the incident subgraph: baselines, deviations, likely origin.
  • Returns a diagnosis, a recovery check and real MLOX actions.
  • Routine actions run on their own; critical ones wait for approval.

6Break it

One command, one hidden fault.

Typing on shifts the first principal component inside pca.transform. Every request still returns 200 OK; only the answers are wrong.

What MLOX is not told: the fault flag is never part of the telemetry. MLOX has to work out where the problem is from the step observations alone.

What this shows

Self-hosted ML with an operator built in.

Zero setup monitoringPipelines, baselines and incidents come from telemetry the model already emits.
Root cause, fastEarly detection finds the broken step in seconds; the reasoning model explains it and proposes a fix.
You set the boundariesRoutine actions run on their own, critical ones wait for a person, and every step is logged.
Our own reasoning modelsCompact ternary-weight models that merge both steps into one and spend compute only when an incident needs it.
From diagnosis to fixThe pipeline observer hands a confirmed fault to a specialist: an ML engineer agent that retrains and redeploys, or an infrastructure agent that updates or rolls back services.
Autonomy with limitsEvery agent gets scoped permissions: what it may do alone, and what needs a sign-off.
